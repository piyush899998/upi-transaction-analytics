# Automated UPI Transaction Analytics Pipeline

**A runnable, local-first simulated payment monitoring project:** Python ETL · PostgreSQL · anomaly detection · SMTP alerts · Streamlit dashboard · Power BI-ready SQL and DAX. No real payments or bank APIs are involved.

## What works

- Reproducible 90-day synthetic UPI-style event stream across 4 fictional/demo-labelled bank segments (`HDFC`, `SBI`, `ICICI`, `AXIS` labels are only simulation labels). The last completed UTC hour includes a controlled **ICICI failure spike** and **SBI volume drop**.
- CSV validation, rejected-row accounting, idempotent `transaction_id` upserts (duplicates never count as new transactions), historical import audit trail, secure parameterized database queries.
- Robust median volume baselines and statistical monitoring against the **same UTC hour on up to 7 preceding days** with configurable thresholds, minimum sample sizes, and deduplicated alert records.
- Email alerts through SSL/TLS authenticated SMTP, optional (all alert records remain visible without SMTP). Non-configured SMTP never blocks analytics.
- Autonomous worker running every 15 minutes by default; once bootstrapped it generates the previous completed hour's simulated traffic and imports it. Its logs show detections and notification outcomes.
- Interactive Streamlit dashboard at `http://localhost:8501`: KPI tiles, bank selector, date range, trends, failure reasons, incident list, ETL health.
- Power BI schema views, browser-friendly CSV export, M connection template, DAX measures and report/refresh instructions in `powerbi/`.
- Unit tests, CI, lint configuration, SQL query examples, sample `.env`.

**Important limitations:** No `.pbix` file is embedded. Creating a native Power BI report and configuring Power BI Service scheduled refresh requires Microsoft Power BI Desktop/Service and appropriate network/driver/gateway access. SMTP requires your own credentials. PostgreSQL and actual SMTP delivery could not be integration-tested in the build environment, where Docker/PostgreSQL services and credentials were unavailable.

## Advanced additions

- 90-day deterministic, synthetic UPI-style history by default, with weekend/hourly volume curves, bank-specific baseline failure rates, category-aware transaction amounts and controlled demo incidents.
- A robust median historical volume baseline, preserving existing transparent failure-rate rules.
- Auditable incident workflow (`OPEN` → `INVESTIGATING` → `RESOLVED`) and notes/assignee in SQL; updates are explicit, never generated by the detector.
- Data-quality/freshness metrics, failure-diagnostics SQL view and an extended Streamlit dashboard.
- `export-powerbi` CLI command to create six CSV tables for Power BI Web. See [`powerbi/WEB_QUICKSTART.md`](powerbi/WEB_QUICKSTART.md). A hosted PostgreSQL connection or gateway is required for truly automated Power BI Service refresh; it is **not** configured by this repository.

## Quick start (Docker, recommended)

Prerequisites: Docker Desktop with Compose, working Docker engine, ports 5432 and 8501 available. Default DB credentials in `compose.yaml` are **local-development only**; change them before network deployment.

```bash
cp .env.example .env
# On Windows PowerShell: Copy-Item .env.example .env

docker compose up --build -d
# The worker automatically initializes tables, seeds demo history and detects incidents.
docker compose logs -f worker
```

Then browse **http://localhost:8501**. Initial import may take a short while depending on disk/CPU; refresh the dashboard after the worker has populated the database.

Re-run the full demo on demand:

```bash
docker compose exec worker python -m upi_analytics.cli demo
```

Inspect alerts and ingestion metrics inside the dashboard. You should see the ICICI failure-spike incident and the SBI volume-drop incident for the latest completed UTC hour, as long as the simulation contains sufficient history and the thresholds are unchanged. Alert uniqueness makes repeated detection idempotent.

Stop services: `docker compose down`. To **erase all sample data**, `docker compose down -v` (destructive).

## Recruiter quick demo (Windows / macOS / Linux)

**No Python installation, PostgreSQL installation, API keys, or Power BI account required** to explore the working Streamlit dashboard. Install [Docker Desktop](https://www.docker.com/products/docker-desktop/), start it, and run these commands from a terminal in the cloned repository:

```bash
git clone https://github.com/piyush899998/upi-transaction-analytics.git
cd upi-transaction-analytics
docker compose up --build -d
docker compose ps
```

Open **http://localhost:8501**. On first launch the worker creates the schema and synthetic history; if the dashboard initially reports no data, wait for the worker to finish and refresh. Inspect progress with:

```bash
docker compose logs --tail=60 worker
```

**If ports 5432 or 8501 are already in use** (common if you run other PostgreSQL/Streamlit projects): edit only the host side of the mappings in `compose.yaml`. Under `db`, change `"127.0.0.1:5432:5432"` to `"127.0.0.1:5433:5432"`; under `dashboard`, change `"127.0.0.1:8501:8501"` to `"127.0.0.1:8502:8501"`. Then run `docker compose up -d` and open **http://localhost:8502**. Keep the right-hand container ports unchanged: PostgreSQL listens on **5432** inside Docker and Streamlit on **8501**. If another service also uses 5433 or 8502, choose other free *host* ports.

**Demo the anomaly logic** by opening the Alerts section, selecting all banks and the 90-day lookback, and showing the seeded ICICI failure spike and SBI traffic drop. Run `docker compose exec worker python -m upi_analytics.cli demo` to repeat the deterministic demo and observe duplicate protection. Data is synthetic; no banking credentials are needed.

**Stop without deleting data:** `docker compose down`. **Permanently delete the demo database volume:** `docker compose down -v` (destructive). Optional email notifications and Power BI reporting are separate enhancements and not required for this walkthrough.

## Email alert configuration

In `.env` add SMTP credentials:

```dotenv
SMTP_HOST=smtp.gmail.com
SMTP_PORT=465
SMTP_USERNAME=your_account@gmail.com
SMTP_PASSWORD=your_app_password
SMTP_FROM=your_account@gmail.com
ALERT_TO=recipient@example.com
SMTP_USE_SSL=true
```

For Gmail, use a valid Google App Password where available (not your normal login password). Never commit `.env`. Set recipient to an inbox you control or have permission to email. The email body explicitly states that the incident is **simulated**. After setting the values, restart the worker with `docker compose up -d --force-recreate worker`, then `docker compose exec worker python -m upi_analytics.cli notify` to retry pending alerts. Three delivery attempts maximum are logged per alert; a previously sent alert is not sent again.

## Quality checks and anomaly rules

Success and failure rates use **resolved transactions** (`SUCCESS + FAILED`) as the denominator. `PENDING` is tracked separately. Payment value KPI sums **successful** payment amounts, not all attempted amounts.

Default detection criteria, per bank/hour:

- **Failure spike:** at least 20 resolved transactions, current failure rate ≥18%, ≥2.5× baseline, and ≥8 percentage points higher than baseline.
- **Volume drop:** baseline mean volume ≥20 transactions and current count <55% of baseline.
- Baseline is the identical hour of day over the preceding **seven calendar days**, and requires at least **three observed historical days**.
- Severity is CRITICAL for ≥30% failure rate or volume <30% of normal; WARNING otherwise.
- Anomaly dedupe key is `(kind, bank, bucket_start)`.

This is transparent rule-based monitoring, not a machine-learning prediction system. Real payment systems would need bank calendars, traffic seasonality, late-arriving event handling, refunds/reversals, event deduplication policies, error-class taxonomy, data governance, alert acknowledgment and true service-level telemetry.

## Design notes

```text
src/upi_analytics/simulator.py    Reproducible synthetic event generator
src/upi_analytics/etl.py          Validation + idempotent ingest + audit trail
src/upi_analytics/db.py           PostgreSQL schema initialization
src/upi_analytics/detection.py    Hourly historical baseline anomaly detection
src/upi_analytics/notifier.py     SMTP notifications and retry state
src/upi_analytics/cli.py          CLI, demo bootstrap, scheduler
src/upi_analytics/dashboard.py    Live browser dashboard
sql/001_schema.sql               Indexed OLTP tables and reporting views
sql/002_analysis_examples.sql     SQL interview examples
powerbi/                         Power BI connectors, measures and setup
```

The simulator is deterministic per seed + UTC hour + bank, including the generated transaction IDs, making repeated imports safe. The scheduler uses a sliding latest-completed-hour window. A missed scheduled hour is not backfilled automatically: use the `generate` and `ingest` commands to backfill a historical time period. Also note that `DEMO_INCIDENTS=true` affects **history generation only**; recurring live simulation uses normal baseline traffic by default.

## Security

This repository uses **synthetic data only**. Passwords should be held in environment variables, no personal contact or payment identifiers are required, PostgreSQL is bound to local host by default, and SMTP uses TLS. The bundled PostgreSQL credentials are insecure for production; do not deploy publicly without proper database secrets, access control, backups, and network isolation.

## Incident management

```bash
# Replace 1 with an actual alert id from v_incident_timeline.
docker compose exec worker python -m upi_analytics.cli incident --id 1 --status INVESTIGATING --assignee analyst --notes "Investigating simulated timeout"
docker compose exec worker python -m upi_analytics.cli incident --id 1 --status RESOLVED --notes "Synthetic incident resolved"
# Export all six Power BI data tables from PostgreSQL.
docker compose exec worker python -m upi_analytics.cli export-powerbi
```

**Note:** At 90 days × 4 banks × ~36/hour, generating and importing the first demo may be substantial. To run a quick demo, set `SIMULATION_DAYS=8` in `.env` before first startup. To preserve any previous database data, don't run `docker compose down -v`.
